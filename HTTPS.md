# Работа по HTTPS

Сейчас система работает по обычному HTTP: пароли и данные идут по сети
предприятия открытым текстом.

Здесь — весь порядок перехода на шифрованное соединение: когда он
нужен, что делать по шагам, как проверить, что получилось, и что
делать, если не получилось.

## Нужно ли это вам

**Внутри предприятия можно оставить как есть.** Чтобы прочитать пароль
кладовщика, посторонний должен уже находиться в вашей сети со своим
устройством и уметь слушать чужой трафик. Если сеть закрыта, а система
наружу не выставлена, шифрование мало что добавляет, зато прибавляет
хлопот: сертификат, его срок, настройка на каждом рабочем месте.

**Переходить стоит, если верно хоть одно:**

| Случай | Почему |
|---|---|
| Система открыта из интернета | Обязательно. Без шифрования пароль виден любому узлу по пути |
| В сети бывают чужие устройства | Гости с ноутбуками, открытый Wi-Fi, подрядчики |
| Сотрудники заходят через Wi-Fi | Беспроводную сеть слушать проще, чем провод |
| Этого требует порядок предприятия или проверяющие | Тут обсуждать нечего |

Переход занимает около получаса и делается один раз. Данные он не
затрагивает: ни база, ни фотографии, ни настройки учёта не меняются.

## Как это будет устроено

Сейчас браузер сотрудника обращается прямо к системе:

```
Браузер  →  Складская система (порт 8000)
```

Станет так: впереди встанет nginx. Он берёт на себя шифрование, а с
системой разговаривает внутри того же компьютера, где слушать нечего:

```
Браузер  →(https, порт 443)→  nginx  →(http, порт 8000)→  Складская система
```

Сама система при этом продолжает работать как работала. Она только
узнаёт от nginx, что снаружи было шифрование, — и начинает вести себя
соответственно: помечать куки, перенаправлять обращения по http.

Из этого следует важное: **систему после установки nginx не нужно
выставлять наружу напрямую**. Порт 8000 остаётся доступным только на
самом компьютере, наружу смотрит только nginx.

---

## Что понадобится

1. **nginx для Windows** — с nginx.org, «stable version», архив
   `nginx-1.xx.x.zip`. Установки не требует: распаковывается в папку и
   запускается.
2. **Сертификат** — выпустите своим же скриптом, платить не за что.
   Ничего доустанавливать для этого не нужно: скрипт обходится
   средствами Windows, интернет ему тоже не требуется.
3. **Полчаса** и права администратора на компьютере с системой.

### Про купленный сертификат

Он здесь не нужен и чаще всего невозможен. Сертификаты выдают на имена,
существующие в интернете (`sklad.leko.ru`), а внутреннее имя вроде
`sklad.leko.local` или адрес `192.168.1.50` не подтвердит ни один
удостоверяющий центр — им нечего проверять.

Покупать имеет смысл, только если систему открывают наружу под
настоящим доменным именем. Тогда порядок тот же, но вместо шага 2
кладутся файлы от поставщика сертификата, а шаг 6 не нужен вовсе.

## Шаг 1. Поставить nginx

**1.1.** Скачайте архив с nginx.org и распакуйте, например, в
`C:\nginx`. Внутри должны оказаться `nginx.exe` и папки `conf`, `html`,
`logs`.

**1.2.** Проверьте, что он вообще запускается:

```powershell
cd C:\nginx
.\nginx.exe -t
```

Ответ `syntax is ok` и `test is successful` означает, что всё на месте.

**1.3.** Убедитесь, что порт 443 свободен:

```powershell
Get-NetTCPConnection -State Listen -LocalPort 443 -ErrorAction SilentlyContinue
```

Пусто — хорошо. Если что-то занимает порт, обычно это IIS («Службы
IIS» в списке служб) или старый Skype. IIS останавливается так:

```powershell
Stop-Service W3SVC
Set-Service W3SVC -StartupType Disabled
```

**1.4.** Откройте порт в брандмауэре — иначе с других компьютеров
система не откроется:

```powershell
New-NetFirewallRule -DisplayName "Складской учёт HTTPS" `
    -Direction Inbound -Protocol TCP -LocalPort 443 -Action Allow
```

Порт 8000, если он был открыт раньше, теперь можно закрыть: снаружи к
системе ходят через nginx.

## Шаг 2. Выпустить сертификат

Запустите PowerShell **от имени администратора**:

```powershell
cd D:\warehouse_project\deploy\windows
.\СДЕЛАТЬ-СЕРТИФИКАТ.ps1 -Name sklad.leko.local -Address 192.168.1.50
```

- `-Name` — имя, которое сотрудники набирают в браузере;
- `-Address` — адрес компьютера в сети, если заходят ещё и по нему;
- `-Years` — срок, по умолчанию 2 года.

**Имя в сертификате должно совпадать с адресом в браузере.** Если
сотрудники ходят по `https://192.168.1.50`, а в сертификате только
`sklad.leko.local`, браузер будет ругаться не на доверие, а на
несовпадение имени — и это уже не обходится установкой сертификата.
Перечисляйте оба.

Скрипт делает **два** сертификата: свой центр предприятия и выданный
им сертификат сервера. Иначе нельзя: браузер доверяет не самому сайту,
а тому, кто за него поручился, и поручителем должен быть центр.
Сертификат, поручившийся сам за себя, Chrome в этой роли не принимает,
сколько его ни устанавливай.

Из этого следует удобное: на рабочие места ставится сертификат центра,
и живёт он десять лет. Сертификат сервера меняется каждые два года —
обходить рабочие места при этом не нужно.

В `deploy\nginx` появятся три файла:

| Файл | Что это | Куда |
|---|---|---|
| `sklad.crt` | сертификат сервера вместе с сертификатом центра | путь прописывается в nginx |
| `sklad.key` | закрытый ключ | путь прописывается в nginx, **никому не показывать** |
| `sklad-для-сотрудников.crt` | сертификат центра, ключа в нём нет | ставится на рабочие места (шаг 6) |

Закрытый ключ — это и есть вся защита. Кто получил файл `sklad.key`,
тот может выдать себя за вашу систему. Не кладите его в общие папки и
не пересылайте почтой.

## Шаг 3. Настроить nginx

**3.1.** Сделайте настройку под вашу установку:

```powershell
cd D:\warehouse_project\deploy\windows
.\НАСТРОИТЬ-NGINX.ps1 -Name sklad.leko.local -Address 192.168.1.50
```

Скрипт берёт образец `deploy\nginx\warehouse-https.conf`, подставляет в
него ваши пути, имя и адрес и кладёт рядом готовый файл
`warehouse-https.local.conf`. Дальше указывают именно его.

Отдельный файл нужен не для порядка. Образец лежит под git, и правка
прямо в нём останавливала бы обновление системы: git не станет затирать
изменённый файл. Готовая настройка под git не числится — обновления её
не трогают, а она их не держит.

В образце пути написаны для примера (`C:/warehouse_project/...`), и
подставлять их вручную не нужно: у вас программа на другом диске, и
nginx честно ответит, что такого файла нет.

**3.2.** Проверьте настройку до запуска:

```powershell
cd D:\nginx-1.30.4
.\nginx.exe -t -c D:\warehouse_project\deploy\nginx\warehouse-https.local.conf
```

Строка `cd` здесь обязательна. Запись `.\nginx.exe` означает «в этой
папке», и из любой другой Windows ответит, что такое имя не распознано
как имя программы. Подставьте свою папку, если распаковали nginx в
другое место.

**3.3.** Запустите:

```powershell
.\nginx.exe -c D:\warehouse_project\deploy\nginx\warehouse-https.local.conf
```

Окно закроется сразу — так и должно быть, nginx уходит в фон. Проверить,
что он работает:

```powershell
Get-Process nginx
```

Остановить (пригодится при перенастройке):

```powershell
.\nginx.exe -s stop
```

Перечитать настройку без остановки:

```powershell
.\nginx.exe -s reload
```

## Шаг 4. Включить HTTPS в системе

В файле `.env` (в папке программы):

```
USE_HTTPS=True
CSRF_TRUSTED_ORIGINS=https://sklad.leko.local,https://192.168.1.50
ALLOWED_HOSTS=sklad.leko.local,192.168.1.50,localhost,127.0.0.1
```

**`CSRF_TRUSTED_ORIGINS` — то место, где ошибаются чаще всего.**
Перечислите здесь **все** адреса, по которым открывают систему, в
точности так, как они выглядят в адресной строке:

- обязательно с `https://` — с `http://` не сработает;
- с портом, если он не 443: `https://sklad.leko.local:8443`;
- имя и адрес — разные записи. Если ходят и по имени, и по адресу,
  нужны обе.

Если тут ошибиться, система откроется, но **вход будет отвечать
«подделка запроса»** — и понять, почему, без подсказки трудно.

Что включается вместе с `USE_HTTPS=True`:

| Что | Зачем |
|---|---|
| Перенаправление с http на https | Кто набрал старый адрес, попадёт куда надо |
| Куки сессии и защиты от подделки помечаются «только по защищённому соединению» | Главное. Иначе они уйдут и по открытому каналу, где их можно прочитать и войти под чужим именем |
| Браузеру сообщается: на этот адрес полгода ходить только по https | Защищает от подмены при первом обращении |
| Система верит заголовку nginx о шифровании | Иначе она считает соединение незащищённым и перенаправляет по кругу |

После правки `.env` **систему нужно перезапустить** — файл читается
один раз при запуске.

## Шаг 5. Проверить

**5.1. Проверка настроек:**

```powershell
cd D:\warehouse_project
venv\Scripts\python.exe manage.py checksetup
```

Должны появиться строки:

```
✓ Включён режим HTTPS: перенаправление, защищённые куки, HSTS
✓ Доверенные адреса: https://sklad.leko.local, https://192.168.1.50
```

Если вместо этого написано «Включён HTTPS, но не заданы доверенные
адреса» — вернитесь к шагу 4.

**5.2. Проверка в браузере.** Откройте систему по новому адресу и
войдите. Что должно получиться:

- в адресной строке `https://` и замок (или предупреждение о доверии —
  оно снимается на шаге 6);
- вход проходит, страницы открываются;
- если набрать адрес с `http://`, браузер сам переходит на `https://`.

**5.3. Проверка защищённых кук** — необязательно, но убеждает
окончательно. В браузере нажмите F12 → «Приложение» (Application) →
«Файлы cookie». У `sessionid` и `csrftoken` должна стоять галочка
`Secure`.

## Шаг 6. Поставить сертификат на рабочие места

Пока этого не сделано, браузер на каждом компьютере честно говорит:
«подключение не защищено», «этому сайту доверять нельзя». Система при
этом работает — через кнопку «Дополнительно» → «Перейти на сайт».

**Так оставлять нельзя.** Дело не в неудобстве: сотрудник, который
каждый день нажимает «всё равно продолжить», нажмёт её и в тот день,
когда предупреждение окажется настоящим.

Порядок на каждом компьютере (5 минут):

1. Скопируйте на него файл `sklad-для-сотрудников.crt`.
2. Двойное нажатие по файлу → кнопка **Установить сертификат**.
3. Расположение хранилища: **Локальный компьютер** (не «Текущий
   пользователь» — иначе не подействует для других учётных записей).
4. **Поместить все сертификаты в следующее хранилище** → **Обзор** →
   **Доверенные корневые центры сертификации** → ОК.
5. **Далее** → **Готово**. Должно появиться «Импорт успешно выполнен».
6. Закройте и заново откройте браузер.

Предупреждение исчезнет, в адресной строке появится замок.

**Если компьютеры в домене**, это же раздаётся групповой политикой
сразу на все машины: Конфигурация компьютера → Политики → Параметры
Windows → Параметры безопасности → Политики открытого ключа →
Доверенные корневые центры сертификации → Импорт.

**Firefox** имеет собственное хранилище и системному не доверяет:
Настройки → Приватность и защита → Сертификаты → Просмотр сертификатов
→ Центры сертификации → Импортировать.

## Шаг 7. Запускать nginx вместе с компьютером

Запущенный руками nginx не переживёт перезагрузку. Сделайте задание в
планировщике (права администратора):

```powershell
$action = New-ScheduledTaskAction -Execute 'C:\nginx\nginx.exe' `
    -Argument '-c D:\warehouse_project\deploy\nginx\warehouse-https.local.conf' `
    -WorkingDirectory 'C:\nginx'
$trigger = New-ScheduledTaskTrigger -AtStartup
Register-ScheduledTask -TaskName 'nginx для складского учёта' `
    -Action $action -Trigger $trigger -RunLevel Highest `
    -User 'SYSTEM' -Description 'Веб-сервер перед складской системой'
```

Проверьте после следующей перезагрузки, что система открывается сама,
без запуска nginx руками.

## Обслуживание

**Срок сертификата.** По умолчанию два года. Когда он кончится, браузеры
перестанут открывать систему без предупреждения — работа встанет, и
причина будет неочевидной. Поставьте напоминание в календарь **за месяц
до срока**. Посмотреть срок:

```powershell
cd D:\warehouse_project\deploy\nginx
certutil -dump sklad.crt | Select-String "NotAfter"
```

**Замена сертификата** — тот же скрипт из шага 2, затем
`nginx.exe -s reload` и переустановка нового
`sklad-для-сотрудников.crt` на рабочие места.

**Резервные копии.** Сертификат и ключ **не попадают** в резервные
копии системы: копия хранит базу, фотографии и `.env`, а файлы nginx
лежат отдельно. Скопируйте `sklad.crt` и `sklad.key` туда же, где
храните копии, — иначе при восстановлении на другом компьютере
сертификат придётся выпускать заново (это не смертельно, но полчаса).

**Обновление системы.** `ОБНОВИТЬ.bat` работает как раньше и nginx не
трогает. После обновления перезапустите систему; nginx перезапускать не
нужно.

## Если что-то пошло не так

### При входе: «CSRF Failed» или «Ошибка проверки подлинности запроса»

Самая частая. Адрес не перечислен в `CSRF_TRUSTED_ORIGINS` или
перечислен не так: с `http://` вместо `https://`, без порта, по имени
вместо адреса.

Посмотрите, что именно в адресной строке браузера, и впишите ровно это
(до первой косой черты). Перезапустите систему.

### Браузер: «слишком много перенаправлений» или уходит на адрес без порта

nginx не передаёт заголовок `X-Forwarded-Proto https`. Система считает
соединение незащищённым и отправляет браузер на https снова — и так по
кругу.

Проверьте, что в настройке nginx есть строка:

```
proxy_set_header X-Forwarded-Proto https;
```

Она есть в образце; чаще всего её теряют при переписывании настройки
своими руками.

### В окне системы: `You're accessing the development server over HTTPS`

Это не поломка, а обращение не туда: браузер стучится шифрованием прямо
в систему, на порт 8000, минуя nginx. Шифрование там не отвечает — его
делает nginx, — поэтому в окне идут сотни строк с обрывками
непрочитанного.

Причина почти всегда одна: в адресе остался порт. После перехода на
HTTPS открывать нужно **без порта**:

```
https://sklad.leko.local          — верно
https://sklad.leko.local:8000     — сюда браузер и стучится зря
```

Порт 8000 теперь внутренний: по нему с системой разговаривает только
nginx, на том же компьютере. Проверьте заодно закладки и ярлыки на
рабочих местах — старый адрес с портом обычно сохранён именно там.

Если и без порта не открывается, значит nginx не запущен:

```powershell
Get-Process nginx
```

### nginx: `CreateFile() ".../mime.types" failed`

Настройка искала файл `mime.types` рядом с собой, а он лежит в папке
nginx. Так было в образце до августа 2026 года. Обновите систему —
теперь виды файлов перечислены прямо в настройке, и посторонних файлов
она не требует:

```powershell
cd D:\warehouse_project
git pull
```

Если обновиться сейчас нельзя, есть равноценный обходной путь: указать
nginx его собственную папку ключом `-p`:

```powershell
cd D:\nginx-1.30.4
.\nginx.exe -t -p D:\nginx-1.30.4\ -c D:\warehouse_project\deploy\nginx\warehouse-https.conf
```

### nginx: `cannot load certificate ... no start line` (PEM_read_bio_X509_AUX)

Файл `sklad.crt` пуст или лежит в другом виде — nginx не нашёл в нём
строки `-----BEGIN CERTIFICATE-----`. Посмотрите сами:

```powershell
Get-Content D:\warehouse_project\deploy\nginx\sklad.crt -TotalCount 1
```

Пусто — значит файл нулевой длины.

Так было со скриптом до августа 2026 года: он звал для перекладывания
стороннюю программу openssl, а её на складском компьютере нет — вместе
с nginx для Windows она не идёт. Отказ скрипт не замечал и оставлял
пустой файл, отчитавшись «Готово». Обновите систему и выпустите
сертификат заново:

```powershell
cd D:\warehouse_project
git pull
cd deploy\windows
.\СДЕЛАТЬ-СЕРТИФИКАТ.ps1 -Name sklad.leko.local -Address 192.168.1.50
```

Теперь и сертификат, и ключ записываются средствами самого Windows,
никаких посторонних программ не нужно, а получившиеся файлы скрипт
проверяет перед тем, как отчитаться.

Не путайте с `sklad-для-сотрудников.crt`: он в двоичном виде — для
Windows, — и nginx его тоже не прочтёт. В настройке nginx должен
стоять `sklad.crt`.

### Браузер: «подключение не защищено» (ERR_CERT_AUTHORITY_INVALID)

Так и должно быть, пока не выполнен шаг 6. Сертификат выпущен вашим
предприятием, а браузер о нём не знает. Поставьте
`sklad-для-сотрудников.crt` на рабочие места.

**Если сертификат уже поставлен, а браузер всё равно не доверяет** —
он выпущен скриптом до августа 2026 года. Тогда выпускался один
сертификат, сам себе поручитель, а браузер требует, чтобы поручителем
был центр — сертификат с пометкой «может выдавать другие». Установка
такого в «доверенные корневые центры» ничего не даёт: Chrome его в этой
роли не принимает.

Лечится перевыпуском — теперь делается свой центр предприятия и
выданный им сертификат сервера:

```powershell
cd D:\warehouse_project
git pull
cd deploy\windows
.\СДЕЛАТЬ-СЕРТИФИКАТ.ps1 -Name sklad.leko.local -Address 192.168.1.50
cd D:\nginx-1.30.4
.\nginx.exe -s reload
```

Затем на рабочих местах удалить старый и поставить новый
`sklad-для-сотрудников.crt` — теперь это сертификат центра, и менять
его придётся раз в десять лет, а не с каждым перевыпуском.

### Браузер: «сертификат выдан для другого имени» (ERR_CERT_COMMON_NAME_INVALID)

Обращаются по адресу, которого нет в сертификате: например, по
`192.168.1.50`, когда в сертификате только имя. Выпустите сертификат
заново, перечислив оба (`-Name` и `-Address`).

Если сертификат уже выпущен с `-Address`, а по адресу браузер всё
равно не доверяет — сертификат сделан скриптом до августа 2026 года.
Адрес в нём записан как имя, а браузер, открывая `https://192.168.1.50`,
ищет запись именно вида «адрес» и такой не находит. Установка
сертификата на рабочее место в этом случае не помогает: дело не в
доверии. Обновитесь и выпустите заново:

```powershell
cd D:\warehouse_project
git pull
cd deploy\windows
.\СДЕЛАТЬ-СЕРТИФИКАТ.ps1 -Name sklad.leko.local -Address 192.168.1.50
```

Посмотреть, что записано в нынешнем сертификате:

```powershell
certutil -dump D:\warehouse_project\deploy\nginx\sklad.crt | Select-String "Subject Alternative"  -Context 0,3
```

Должны быть обе строки — `DNS Name=sklad.leko.local` и
`IP Address=192.168.1.50`. Если адрес стоит после `DNS Name=` —
это тот самый случай.

**Проще же всего ходить по имени.** Адрес в сертификате нужен только
тем, кто набирает его в браузере; если все заходят по
`https://sklad.leko.local`, `-Address` можно не указывать вовсе.

### Страницы открываются, но без оформления — голый текст и ссылки

Система работает, а nginx не находит файлы оформления: неверен путь в
строках `alias` для `/static/` и `/media/`. Ошибки при этом никакой не
видно — nginx молча отвечает «не найдено» на каждый файл стилей, и
браузер показывает страницу как есть.

Проверить прямо:

```powershell
curl.exe -k -o NUL -w "%{http_code}`n" https://sklad.leko.local/static/admin/css/base.css
```

`200` — файлы на месте, дело в другом. `404` — путь неверен.

Две причины, обе частые:

1. В путях обратная косая черта. В настройке nginx пишется прямая:
   `D:/warehouse_project/staticfiles/` — и с косой чертой на конце.
2. Не собраны сами файлы. Соберите:

```powershell
cd D:\warehouse_project
.\venv\Scripts\python.exe manage.py collectstatic --noinput
```

Это же нужно повторять после каждого обновления системы.

### Система вообще перестала открываться после `USE_HTTPS=True`

Скорее всего nginx не запущен или слушает не тот порт. Поставьте в
`.env` обратно `USE_HTTPS=False`, перезапустите систему, убедитесь, что
она работает по http, и разбирайтесь с nginx отдельно.

### nginx не запускается

```powershell
cd C:\nginx
Get-Content logs\error.log -Tail 20
```

Частые причины: занят порт 443 (см. шаг 1.3), неверный путь к
сертификату, обратная косая черта в путях вместо прямой.

### Работает у вас, но не с других компьютеров

Не открыт порт 443 в брандмауэре (шаг 1.4) или имя `sklad.leko.local`
не разрешается в адрес. Проверьте с другого компьютера:

```powershell
Test-NetConnection sklad.leko.local -Port 443
```

Если имя не находится, впишите его в `C:\Windows\System32\drivers\etc\hosts`
на рабочих местах или заведите запись на своём сервере имён.

## Как вернуть как было

Отключить шифрование можно в любой момент: поставьте в `.env`
`USE_HTTPS=False` и перезапустите систему. Она снова будет работать по
http на порту 8000.

**Но есть тонкость, о которой стоит знать заранее.** Пока HTTPS был
включён, браузеры получили указание ходить на этот адрес только по
https — и помнят его полгода. После отката они откажутся открывать
систему по http, причём без внятного объяснения.

Выход — либо оставить nginx работать (система прекрасно живёт за ним и
без `USE_HTTPS=True`), либо стереть эту память в браузере:

- **Chrome, Edge:** откройте `chrome://net-internals/#hsts`, в поле
  «Delete domain security policies» впишите имя (`sklad.leko.local`) и
  нажмите Delete;
- **Firefox:** «Журнал» → «Удалить историю» → «Настройки сайтов».

Поэтому и советуют сначала пожить с HTTPS неделю-другую, прежде чем
считать переход окончательным.

## Что из этого проверено

Проверено на деле, а не по документации:

- система, поднятая за nginx с самодельным сертификатом, работает
  целиком: вход, все разделы, витрина; ошибок в браузере нет;
- обращение по http перенаправляется на https;
- куки сессии и защиты от подделки приходят с пометкой «только по
  защищённому соединению»;
- статика и фотографии, отданные nginx, доходят до браузера с верной
  пометкой вида файла (`text/css`, `image/png`), причём настройка
  проверена там, где файла `mime.types` рядом нет вовсе; а при неверном
  пути в `alias` отдаётся «не найдено» — страница открывается без
  оформления, никакой ошибки при этом не видно;
- ошибка с адресами в `CSRF_TRUSTED_ORIGINS` действительно даёт отказ
  при входе — на неё наткнулись при проверке, и теперь `checksetup`
  предупреждает о ней заранее;
- потерянный заголовок `X-Forwarded-Proto` действительно уводит браузер
  на адрес без порта;
- без установленного сертификата соединению не доверяют, с
  установленным — доверяют;
- обращение по имени, которого нет в сертификате, отклоняется;
- откат к `USE_HTTPS=False` при работающем nginx проходит без потерь;
- сборка файлов сертификата и ключа из скрипта выпуска — она выполнена
  на PowerShell и проверена запуском: получившийся ключ совпадает
  побайтно с выгрузкой средствами самой платформы, nginx принимает пару
  и отдаёт страницу и по имени, и по адресу.

**Чего проверить было нельзя** и что остаётся на вашей стороне: сам
Windows — выпуск сертификата через `New-SelfSignedCertificate`,
установка его в хранилище рабочих мест, задание в планировщике и
правила брандмауэра. Команды выверены по документации Microsoft, но
выполнялись не на Windows, а образец настройки nginx и поведение самой
системы проверены запуском.
