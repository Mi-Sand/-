# Исправление критических проблем: PostgreSQL и SECRET_KEY

Инструкция по двум обязательным правкам, выявленным при аудите:
переход с SQLite на PostgreSQL и замена ключа безопасности.

Обе делаются один раз и занимают около 15 минут.

---

## Проблема 1. Система работает на SQLite вместо PostgreSQL

### Почему это важно

В файле `.env` стоит `DB_ENGINE=sqlite`. Все данные (товары, документы,
остатки, сотрудники, чат) лежат в файле `db.sqlite3`, а настроенная вами
база PostgreSQL не используется.

SQLite при записи **блокирует базу целиком**. Пока один сотрудник
проводит документ, остальные ждут. При работе нескольких человек с разных
компьютеров начнутся ошибки «database is locked».

PostgreSQL таких ограничений не имеет — он и создан для многопользовательской
работы.

### Как перенести данные (без потерь)

Все команды выполняются в папке проекта с активированным venv
(в начале строки видно `(venv)`).

**Шаг 1. Выгрузить текущие данные из SQLite**

Убедитесь, что в `.env` пока стоит `DB_ENGINE=sqlite`, и выполните:

```powershell
python manage.py dumpdata --natural-foreign --natural-primary -e contenttypes -e auth.Permission -e admin.logentry -e sessions --indent 2 -o backup_data.json
```

Появится файл `backup_data.json` — это все ваши данные. **Не удаляйте его.**

Проверьте, что файл не пустой:

```powershell
dir backup_data.json
```

Размер должен быть больше нуля (обычно десятки килобайт).

**Шаг 2. Переключиться на PostgreSQL**

Откройте `.env`:

```powershell
notepad .env
```

Замените строку `DB_ENGINE=sqlite` на:

```
DB_ENGINE=postgres
```

Убедитесь, что рядом заполнены реквизиты вашей базы:

```
DB_NAME=warehouse_db
DB_USER=warehouse_user
DB_PASSWORD=ваш_пароль_от_warehouse_user
DB_HOST=localhost
DB_PORT=5432
```

Сохраните (Ctrl+S) и закройте.

**Шаг 3. Создать таблицы в PostgreSQL**

```powershell
python manage.py migrate
```

Django создаст все таблицы в пустой базе PostgreSQL.

**Шаг 4. Загрузить данные**

```powershell
python manage.py loaddata backup_data.json
```

Должно вывести что-то вроде `Installed NNN object(s)`.

**Шаг 5. Проверить**

```powershell
python manage.py runserver 0.0.0.0:8000
```

Зайдите в систему — все товары, документы и остатки должны быть на месте.
Проверьте страницу «Отчёты» → «Остатки».

### Если что-то пошло не так

Данные никуда не делись: файл `db.sqlite3` остался нетронутым. Чтобы
вернуться к SQLite, просто поменяйте в `.env` обратно на
`DB_ENGINE=sqlite` — всё снова заработает как раньше.

### Частые ошибки

**`password authentication failed for user "warehouse_user"`**
Пароль в `.env` не совпадает с тем, что задан в PostgreSQL. Проверьте
пароль в pgAdmin или задайте новый.

**`database "warehouse_db" does not exist`**
База не создана. Откройте pgAdmin → Databases → правой кнопкой → Create →
Database → имя `warehouse_db`.

**`permission denied for schema public`**
У пользователя нет прав на базу. В pgAdmin: правой кнопкой на
`warehouse_db` → Properties → Security → добавьте `warehouse_user`
с привилегией ALL.

**При loaddata ошибка про дубликаты**
База не пустая (вы уже что-то в неё записали). Очистите её и повторите:
```powershell
python manage.py flush --no-input
python manage.py loaddata backup_data.json
```

## Проблема 2. Ключ безопасности не изменён

### Почему это важно

В `.env` стоит `SECRET_KEY=your-super-secret-key-change-this-in-production` —
это значение из шаблона, оно известно всем.

Этим ключом Django подписывает сессии пользователей и токены. Зная его,
злоумышленник может подделать сессию и войти под любым сотрудником,
включая администратора.

### Как исправить

**Шаг 1. Сгенерировать новый ключ**

```powershell
python -c "import secrets,string; print(''.join(secrets.choice(string.ascii_letters+string.digits+'!@#$%^&*(-_=+)') for _ in range(60)))"
```

Команда выведет случайную строку из 60 символов. Скопируйте её.

**Шаг 2. Вписать в .env**

```powershell
notepad .env
```

Замените строку SECRET_KEY на свою:

```
SECRET_KEY=сюда_вставьте_сгенерированную_строку
```

Сохраните и закройте.

**Шаг 3. Перезапустить сервер**

```powershell
python manage.py runserver 0.0.0.0:8000
```

После смены ключа все активные сессии сбросятся — нужно будет войти
заново. Это нормально.

### Важно

Файл `.env` не должен попадать в архивы, репозитории и никому
пересылаться — в нём пароль базы и ключ безопасности. В `.gitignore` он
уже указан.

## Проверка, что всё получилось

```powershell
python manage.py check
```

Ошибок быть не должно.

Затем зайдите в систему и убедитесь:
- товары и остатки на месте;
- документы приход/расход отображаются;
- вход работает (после смены ключа — заново);
- в «Отчётах» цифры совпадают с тем, что было.

## Что ещё исправлено в этом обновлении

- **Запрет удаления проведённых документов.** Раньше можно было удалить
  проведённый приход, и товар оставался на складе без основания — учёт
  разъезжался. Теперь такой документ удалить нельзя.
- **Отмена проведения (сторно).** У проведённого документа появилась
  кнопка «↩ Отменить» — она корректно откатывает остатки. Для прихода
  откат невозможен, если товар уже израсходован (система предупредит).
- **Запрет редактирования проведённых документов** — по той же причине.
- **requirements.txt приведён в порядок:** заменён неработающий
  `psycopg2-binary` на `psycopg[binary]`, добавлен `Pillow` (без него
  не работают фото товаров).
